# 1688 图片匹配逐小时速率测试

用户于 2026-10-12 授权：新导入批次从 90 次/小时开始，每档持续一小时，无滑块验证再增加 10 次/小时。

## 运行规则

- 配置后处于 waiting。只有新批次通过原有产品筛选并进入1688匹配、发起首个实际搜索预留时，才开始当前小时计时；不重跑已完成产品。
- 90、100、110 次/小时分别使用至少 40,000、36,000、32,728 毫秒的启动间隔。全程单任务串行，试验期间替代默认每10次额外休息；HTTP 429仍按 Retry-After 或至少5分钟退避。
- 一小时结束后的下一次搜索前，检查上一档的实际样本数和结果。达到该档所需次数、没有验证暂停、没有长时间观测中断，才增加10次/小时。
- 样本不足时标记 throughput_limited，保持当前速率并继续记录，不将目标速率当作已验证的实际吞吐。长时间空闲、服务重启和429导致中断，该段不会成为通过记录；重新有任务时重测当前档。
- 首次滑块/访问验证立即暂停队列，保留任务断点及 trigger。人工完成验证和明确恢复之前不再搜索；恢复队列也不会自动重启递增试验。
- 宿主后台按 nextRetryAt 精确唤醒，保留5秒巡检兜底、人工暂停和单任务互斥。

## 指标口径

rateTrial.currentStage 与 history 记录目标、开始/结束时间、started、succeeded、failed、pending，以及实际发起/成功次数折算每小时。started是实际搜图预留次数，含重试，不是去重产品数；succeeded表示桥接已返回候选，最终产品匹配还包含下载图片、比较和保存报价。

trigger 冻结验证发生时的目标速率、实际次数、经过时长、折算速率及上一档完整通过的速率。它只能说明当次账号/会话和条件下的观察，不能证明固定的全局验证码阈值。若第一档就遇到验证，尚无通过档位。

## 本地接口和持久化

- GET http://127.0.0.1:16880/api/v1/queue/rate-trial：只读速率状态。
- POST 同地址，JSON为 {"confirmed":true,"startPerHour":90,"stepPerHour":10,"stageDurationMs":3600000}；重复相同参数幂等，不重置记录或解除暂停。
- GET http://127.0.0.1:16880/api/v1/runtime：只读队列，不加verify参数。
- 状态保存在实际采购桥接目录 data/sourcing-console/runtime-cache/image-search-rate-policy.json，原子写入；不修改产品人工价格、重量、采购成本或供应商报价。

## 验证

隔离策略测试覆盖90→100→110、空队列、重启、断档、持久化、吞吐不足、滑块和429；桥接集成测试覆盖启用接口与真实执行分支的结果记账。宿主虚拟时钟测试验证36秒到期即发起下一项，保留暂停和重启断点。

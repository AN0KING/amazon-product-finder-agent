## 代码原因

1. `lib/profit-model.mjs:89-96`：采购成本缺失时利润计算返回 `null`。补齐有效成本后，已有同步计算链会计算利润，无需另建“利润计算任务”。页面中的目标采购成本/盈利线不能替代实际或明确标注来源的参考采购成本。
2. `app.js:4578-4584`：待续商品只来自当前 `runState.supplier1688Pipeline.productIds` 与当前 `products` 的交集。当前批次没有匹配范围，因此返回空列表。
3. `app.js:4637-4638`、`4830-4833`：待续列表为空时直接返回，并停止续跑计时器；不会检查历史暂停批次。
4. `app.js:1802-1813`、`1834-1846`：页面初始化从 `/api/state.latestRun` 恢复并替换当前批次。`lib/persistence-store.mjs:407` 优先选择 `latestRunId`。
5. `app.js:1954`：快照恢复的自动续跑仅调用 Amazon 恢复入口，没有同时重建 1688 续跑计时器。

现有证据能够确认当前批次与原暂停批次不同。普通后台轮询有批次 ID 保护，不能据此认定它直接把原批次切换走；具体切换发生于页面重载还是手动载入历史记录，现有日志不足以确定。

## 对应修复范围

- 让已确认的 1688 匹配范围按原批次持久化续跑，避免依赖当前页面正在查看哪个批次。
- 在恢复原批次时重新绑定已有采购任务，先取回已完成结果，再继续剩余 395 项，避免重复搜图。
- 保存并正确回传采购任务 ID、候选筛选结果及报价；成本齐全后自动调用现有利润公式。
- 仍遵守人工暂停与访问验证要求、既有限速和人工成本保护；不能直接把当前页面的 800 项当作原先确认的 395 项启动。

# 采集暂停、匹配中断与控制超时

运行与守护由本机 Node 程序负责，不依赖 AI 会话。v0.9.55 在原恢复机制上增加逐商品有限补查和失败原因展示。

## 判断顺序

先读 `GET /api/version` 和 `GET /api/amazon/collection`，再读 `GET /api/1688/pipeline` 与采购服务 `GET /api/v1/runtime`。不使用 health 或 verify 请求作为巡检，也不授权 SellerSprite。

| 状态 | 处理 |
| --- | --- |
| 主服务无法连接 | 核对本项目进程、端口和退出日志，再由已有启动器/守护器恢复；不能仅凭 Failed to fetch 断定被 AI 环境回收 |
| Amazon 普通网络错误或超时 | 保留断点，执行有限重试；成功推进后清除当前错误，历史故障另存 |
| Amazon HTTP 429 | 按后台策略冷却，达到上限后等待用户处理 |
| Amazon 真实访问验证 | 首次明确识别即 needs_attention，关闭自动推进；由用户处理后明确恢复 |
| 人工暂停 | 立即保存暂停意图、停止后续重试，等待当前执行退出；守护和匹配结束不能擅自解除 |
| 本轮 completed | 检查有限补查预算：可恢复访问失败或信息区检查未完成会在原任务内自动补查；已确认页面未提供或预算耗尽时结束并逐商品说明。v0.9.56 起页面 ASIN 差异只作诊断，不阻断字段采集 |
| 1688 技术中断 | 暂停并保留任务，检查服务后明确继续；与滑块、登录失效分别显示 |

验证识别以实际页面表单、可见内容和受限页面结构为依据。正常商品页中脚本包含 WAF/CAPTCHA 字符串，不单独构成访问验证证据。页面不提供月销量、价格或重量时保持未知/未提供，不编造数据。

v0.9.55 的后台 30 秒巡检和显式 `recheck` 使用同一策略：每商品最多额外两次补查，冷却一分钟、两分钟，累计预算随断点保存；刷新、进程恢复和重复巡检均不能重置预算。候选商品旁显示失败原因、补查次数以及耗尽状态。请求有四分钟截止，超时详情保存到相应商品。人工 `retry_missing` 是另一项明确操作，自动巡检不得用它反复重新计数。

## 暂停与页面超时

Amazon 暂停先保存状态并中止请求；所有执行回写在真正提交时复查任务编号和执行代次，过期结果不能覆盖人工暂停。匹配仍须等到 `workerActive=false` 且快照版本同步，才能接管该批商品。

控制请求超时或连接中断不等于后端失败。页面只读查询一次同一 runId 的状态，核对意图及必要的 revision；未知结果显示“操作结果待确认”。同一未确认操作不会因再次点击而重复 POST。控制已确认但快照刷新失败时分别提示，不能从未同步快照启动匹配。

## 1688 执行边界

仍保持单并发及原有速率策略。每次自动搜图由独立的受控 Node 工作进程执行，3 分钟截止只覆盖搜图执行，不包含排队、冷却或人工验证。超时只终止本次拥有的进程树；无法确认退出时保持阻塞，不能冒险启动另一项。

- `SEARCH_TIMEOUT`：执行超过截止。
- `SEARCH_WORKER_EXITED`：进程提前退出，未取得结果。
- `SEARCH_WORKER_STOP_FAILED`：无法确认执行进程停止。
- `SEARCH_INTERRUPTED`：服务重启时发现遗留 running，无法确定平台是否已接受请求。

上述情况不会自动重复搜图。用户检查后明确继续，只恢复对应 blockedTaskId，保持原任务 ID。验证码/登录仍走原人工处理流程，不因技术暂停入口跳过验证。

## 大任务持久化与备份

超过 1 MB 的任务在下一次正常写入时转换为分区存储；只读访问不主动迁移。主 JSON 保存索引，商品、采集结果、控制状态、店铺断点和查询历史分别保存。轻量状态查询与暂停不再读写全部商品。分区内容写完后原子提交主索引，缺失或损坏的分区会报错，不能静默丢弃人工数据。

**备份或复制时，任务 JSON 与同名 `.json.parts` 目录必须一起保留。** 建议服务停止或进入安全维护状态后备份整个 data 目录。页面任务下载会生成可独立读取的完整 JSON。不要用只支持旧格式的版本直接修改新格式任务；回滚需同时恢复升级前的数据备份。

## 本次验证边界

本机检查时当前批次有 251 个商品，processed=251、pending=0，实际状态 completed；旧版本却还返回历史超时 lastError。因此不能把这条旧错误当作当前仍被 Amazon 验证拦截的证据。

本机最大历史 JSON 为 116,465,343 字节，在隔离副本中测得：旧整文件读取与解析约 721 ms，首次分区迁移约 1.19 s；分区后 5 次状态读取约 18–45 ms，暂停保存约 101–120 ms。该结果不是所有机器的时延保证，同事描述的 191 MB 文件尚未在本机取得复现。真实历史原文件未为基准测试修改。

修复通过模拟异常页面、迟到回写、暂停/重启、丢失控制响应、分区损坏与原子提交、工作进程超时/退出等回归验证。无需发起真实 Amazon 采集或 1688 搜图来测试控制逻辑。

## 逐商品利润更新（2026-10-13 补充）

详情请求每返回一件，立即提交该件采集结果和利润，再推进下一件；并发批次中慢请求、超时或访问验证不会抹掉已保存的商品。实时通知携带该件的后台计算结果和版本号，界面优先更新对应行；版本断档、切换任务或编辑冲突时读取完整快照核对。普通状态轮询只作断连后的兜底。

AU/CA 超过标准信封最高重量档时按用户指定最高档估费，真实重量用于头程和国内运费，人工费用保持优先。长描述的明确重量标签不再因整体超过 600 字符被丢弃。详见 [FBA 估费规则](fba-rates-au-ca.md)。

## Product information 重量核验

2026-10-13 实际页面 B08PSZMZRQ 的 Item Weight=0.02 Kilograms 位于 display:none 的 Amazon 原生折叠规格表。解析允许当前商品详情区的这类折叠内容，继续排除隐藏模板和推荐商品，保留原始标签/值供核对。v0.9.56 起只以 Item Weight 作为商品重量；页面 ASIN 差异保留为诊断，不再拒绝主商品信息区。完整检查且没有 Item Weight 时才能报告 page_not_provided。旧无完整性证据记录保持待核验，不自动解除暂停。

缺重且信息区尚未完整时，采集器最多通过当前链接的同站点浏览器页面补读一次，与原有补价通道合并；同页有界展开原生信息控件，等待不超过 4.5 秒。完整无重量页不重复访问。补读遇到访问验证或跨站跳转会停止；页面、canonical 或规格的 ASIN 差异不再中断。技术失败保留原成功字段和待核验原因，这不会解除人工暂停或重置补查次数。

完整 Amazon 页面中 body 的 a-aui_template_weblab_cache 样式类不是隐藏模板；详情解析保留这种已确认的正常祖先节点。任务始终使用输入 ASIN 作为保存键，不因页面中的身份观察改变任务范围。

缺少上架日期只作标注，不作为完整度或利润必填项。用户主动启用日期范围时仍按该项筛选，未启用时正常参与分析。详见 [v0.9.56 更新说明](release-0.9.56.md)。

## v0.9.63 看门狗补充

源码启动器与安装版共用被动探测规则。Scout 连续 3 次版本请求无有效响应时，再次确认并替换本项目进程；可运行的同一任务在同一进程连续观察 15 分钟且分页、已处理数、待处理数、最后进展均不变时，再读状态与 revision 后恢复。人工禁用、暂停、验证、未知原因、尚未到期的冷却及 1688 匹配占用不会触发任务卡住恢复。服务整体无响应时无法读取当前任务，但重启不改业务快照，执行器仍按已保存的暂停/验证状态启动。

恢复次数保存在安装目录 logs/supervisor-recovery.json（源码版为 %TEMP%/scout-au/watchdog-recovery.json），每小时最多 5 次启动，重启守护不会清零。恢复前后都检查停止标记与进程归属，避免重复实例。日志和 supervisor-status.json 保留恢复原因或失败原因。

店铺枚举连续三次明确网络错误后的 needs_attention 会安排 5 分钟起、最长 30 分钟的退避；每小时最多记录 5 次恢复安排，窗口满时继续等待。从原店铺分页继续，不重置单商品补查预算。验证码、HTTP 风控、未知错误仍停下等待处理。详情商品仍使用原有有限重试与最多两次额外补查，失败商品保留具体原因并推进其余商品。
